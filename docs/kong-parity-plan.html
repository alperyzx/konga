Closing the gap between Konga and Kong Manager

A field-level audit of what this Konga fork exposes versus what the Kong 3.9 Admin API actually offers, grouped by entity. The roadmap is complete through Phase 10 and has been verified against a live Kong Manager 3.9.3 instance, Konga, and the Kong Admin API.

How these gaps were found. Kong's side is read from the live Admin API and compared with the reachable forms in Kong Manager OSS at localhost:8002 — /endpoints (141 routes) and /schemas/<entity> for each entity, so it reflects your actual 3.9.3 node rather than documentation. Konga's side is read by extracting ng-model bindings from its form templates, then confirming each claimed absence against the whole of assets/js/app/.

Two classes of finding, with different reliability. A field reported missing is reliable: it appears nowhere in the asset tree, which no amount of template indirection can hide. A field reported partial or stale is weaker, because a field that is present may still be unreachable — hidden behind an ng-if version gate, or sitting in a template nothing routes to. Two such findings in an earlier draft of this document were wrong for exactly those reasons and have been corrected below. Verify reachability before acting on any row that is not a plain absence.

The architecture decision behind the order

Because this fork is meant to keep tracking Kong Manager as it moves, the question that matters is not how many Kong versions Konga supports at once but whether Konga learns Kong's data model at runtime or has it compiled in. Phase 2 answers that: learn it at runtime.

The codebase already contains the experiment. Two subsystems have weathered the same five years of Kong drift. The hand-written forms — form-service-013.html, form-route-013.html, form-route-015.html, whose version suffixes are a version matrix already in progress — accumulated 16 missing fields and one stale field that likely breaks writes. The schema-driven plugin engine, written against Kong 0.14, still renders 33 of 45 plugins correctly on 3.9, including plugins that did not exist when it was written. It needs two type handlers, not two hundred fields.

Why this is cheap to extend. /schemas/<entity> returns the same shape as /schemas/plugins/<name> — the same array of single-key objects and the same descriptor vocabulary (type, required, default, one_of, elements, description). The only control type entity schemas need beyond the plugin set is foreign, used 6 times, and each use declares its own reference target. As a bonus, 105 of 116 entity fields carry a description, so Kong supplies the help text and Konga can stop maintaining its own.

Generated, but not fully automatic. A purely generated form is complete and badly organised. Keep the schema as the source of truth for which fields exist, and add an optional per-entity layout file controlling order, grouping, labels and widget choice — which can also declare Konga-only fields such as url and extras. Anything the layout does not name still renders, into an Advanced section. A new Kong field can then never be silently missing; at worst it is unpolished until someone promotes it.

What makes upgrades sustainable is the coverage test rather than the renderer itself: walking /schemas/* and /plugins/enabled and failing on an unhandled type turns a Kong upgrade into a failing build that lists what changed, instead of a user report months later. It also fixes the orderlist class of bug in the other direction, since schema-driven writes only send fields the schema declares.

The cost is real. The first entity converted will take longer than simply editing its form by hand; the return starts with the second and compounds at each Kong upgrade. The risks are that existing forms carry bespoke behaviour the layout override has to absorb, and that this is a refactor inside legacy AngularJS 1.x. Both argue for converting one entity at a time, worst gap first, leaving the others hand-written until their turn — not a big-bang rewrite.
